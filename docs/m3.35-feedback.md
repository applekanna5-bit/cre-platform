# M3.35 feedback implementation

The public feedback page currently explains the intended review process and states that submissions are unavailable. It collects no information and remains outside the sitemap with noindex directives until activation. The production route allowlist does not admit any feedback API or owner dashboard.

## Verify the hosting environment before implementation

| Area | Evidence needed from a separately authorised, nonproduction environment |
| --- | --- |
| Next.js runtime | Confirm that the hosting plan runs a persistent Node.js 24 server, how it starts Next.js, how secrets reach server processes, which reverse proxy headers are trustworthy, and which scheduled worker mechanism is supported. Confirm that pushing the M3.35 feature branch cannot deploy it. |
| MySQL | Provide access to an owner-provisioned, dedicated staging schema through the authorised runtime. Confirm hostname, port, database, TLS requirements, version and transactional support. Use a restricted runtime account and separate migration access. Test connectivity and persistence across process restarts. |
| Backup and restore | Confirm schedule, retention, recovery responsibility and restore procedure. Restore a backup of synthetic submissions to a disposable schema and compare submission, note, status history and notification records. Never restore over live data. |
| Email | Confirm the existence of the authorised `feedback@thecreledger.com` mailbox, authenticated SMTP settings, sender alignment, outbound access, and send limits. Configure the owner's recipient through the server secret store. Verify receipt and retry using synthetic records. |
| Owner identity | Confirm the approved identity provider, stable owner account identifier, callback origin, MFA and recovery arrangement. Use the hosting secret store for client and session secrets. Confirm the retention and deletion policy for submissions and optional contact details. |

## Implementation design pending verification

- Use a server-side POST with allowlisted categories and specializations, required message, optional HTTP(S) public source URL, and optional name and contact. Limit request bytes before parsing, bound individual fields, and validate at the server. Treat submitted URLs as text and never fetch them automatically. Check origin, apply shared rate limits using the verified proxy trust model, and keep request bodies and personal information out of logs and errors.
- Write the submission and a unique notification job in one MySQL transaction. Return confirmation only after commit. Use an idempotency key for form retries. Query through parameterized statements and render submitted content as text.
- Use a maintained OpenID Connect integration with issuer and subject allowlisting and provider-enforced MFA. Require a fresh, revocable server-side session with Secure, HttpOnly, and SameSite cookies. Authorize every owner read and mutation on the server, including detail, search, status updates, notes, and corrections. Apply CSRF protection to mutations, and return private no-store and noindex headers throughout the owner surface.
- Store status history, private notes, and correction references alongside each submission. Use New, Under Review, Accepted, Resolved, and Closed. Paginate owner search and keep responses out of public search indexes and client bundles.
- Use a scheduled outbox worker with bounded batches, exclusive job claims, capped backoff, and a stable message identifier. Send a minimal notice containing a dashboard link or reference only. SMTP provides no end-to-end exactly-once guarantee. Quarantine uncertain delivery outcomes for manual reconciliation instead of retrying them automatically.
- Before enabling the routes, test anonymous submissions, malformed and oversized requests, rate limiting, restart survival, non-owner and expired sessions, CSRF, correction tracking, SMTP failure and recovery, and isolated backup restoration. Apply the existing preview admission rules and add only explicitly tested production route exceptions.

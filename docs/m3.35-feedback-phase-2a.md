# M3.35 Phase 2A feedback development and readiness

The authentication provider design in this historical phase was superseded by [Phase 2D](m3.35-feedback-phase-2d.md).

The form, dashboard, database services and notification worker are developed offline. The form and dashboard are unmounted. No feedback endpoint, authentication callback, scheduler, runtime pool or real mail transport is wired into the app. The public information page retains noindex. The existing proxy admission rules remain unchanged.

## Dependencies and boundaries

- **MySQL2 and server-only** are installed for prepared execution and the server boundary. Supply a dedicated pool through an authorised server composition root. Set the pool and database session to UTC and utf8mb4, use bounded pool/connect timeouts, and leave multiple statements disabled. Require verified TLS for remote database connections. [MySQL2 prepared statements](https://sidorares.github.io/node-mysql2/docs/documentation/prepared-statements)
- **Auth0 Next.js SDK v4** is selected for the Next.js 16 owner integration. SDK installation and callback wiring remain staging work. Use an isolated Auth0 application with owner-only enrollment, MFA with a hardware-backed factor where supported, and an independently tested recovery factor or recovery codes. Disable remembered MFA. Use an SDK-supported durable server-side session store, short idle and absolute lifetimes, Secure/HttpOnly/SameSite cookies and back-channel logout where supported. Verify issuer, immutable subject, expiry, revocation and a provider-issued claim tied to a completed MFA event. Missing or stale evidence denies access. Admit only the necessary exact SDK paths after existing proxy admission. Disable unused profile, access-token and other SDK endpoints. Preview Basic Auth does not grant dashboard access. [Auth0 Next.js 16 integration](https://auth0.com/blog/handling-auth-nextjs16-with-server-actions-middleware/) · [Auth0 SDK configuration](https://github.com/auth0/nextjs-auth0)
- **Nodemailer** is selected for the SMTP transport. It remains unwired. Use authenticated Hostinger SMTP, one secret-configured destination, and verified server TLS with implicit TLS or required STARTTLS as confirmed in hPanel. Set connection, greeting and socket timeouts and a finite process deadline below the worker lease. The notice contains only a reference and a stable Message-ID. [Nodemailer SMTP options](https://nodemailer.com/smtp.html) · [Hostinger Email settings](https://www.hostinger.com/support/1575756-how-to-get-email-account-configuration-details-for-hostinger-email/)
- **Hostinger Cron Jobs** documents finite Node.js scripts under Advanced → Cron Jobs, UTC schedules, a 255-character command limit and a 30-minute run limit. Cron does not automatically receive web app environment variables. Verify Node.js 24 and the actual script and protected environment file paths on the account. Use a direct Node command without introducing a public cron endpoint. [Hostinger Node.js cron documentation](https://www.hostinger.com/support/how-to-run-cron-jobs-for-node-js-websites-at-hostinger/)

## Request and recovery behavior

The future anonymous endpoint requires same-origin JSON POST, the fixed application header, and a cryptographically random idempotency key. Add hosting ingress body and timeout limits, private no-store/noindex headers and denial of cross-origin requests when wiring the service. The service enforces 48 KiB actual body bytes, validates fields and treats submitted URLs as text. Rate limits start at five attempts per client and sixty globally per 15-minute window. Use a hosting-verified address source and a secret HMAC key. Rate checking fails closed. Stage-test address rotation, shared addresses and spoofed forwarding headers. The address adapter and any necessary ingress challenge remain activation work.

The submission, initial New history record, outbox job and idempotency record commit together. Identical retry payloads reuse the previous result. Changed payloads using the same key return a conflict. Owner reads and mutations require a verified session. Owner mutations also require the same-origin guard and correction paths must come from the published inventory. Before wiring, adapt dashboard requests to that guard and apply bounded request parsing, no-store/noindex responses and safe public errors. Keep private content out of bundles, public indexes and logs.

A worker run claims up to five jobs. A locking read and claim write share a transaction, and a per-attempt token prevents stale workers from recording a result. Explicit transient SMTP rejections before DATA can retry after one, five and thirty minutes. Permanent rejection is marked failed. Unknown outcomes and expired leases are quarantined. SMTP acceptance is different from inbox delivery. For recovery, pause the worker, reconcile the stable Message-ID against permitted SMTP or inbox evidence and confirm the original process has stopped. Record the operator decision without overwriting attempt history. Keep uncertain jobs quarantined unless the owner explicitly authorises a resend.

## Exact owner actions before activation

1. Identify and authorise an isolated Hostinger Node.js staging web app and HTTPS origin. Confirm its Node.js version, Next.js launcher, secure environment injection and reverse-proxy trust rules. Confirm the feature branch and staging cannot deploy to production.
2. In staging database controls, provision a dedicated MySQL/MariaDB schema and least-privilege application and worker users, plus separate migration access. Supply connection details via staging secrets. Verify connectivity from the staging launcher, supported InnoDB transactions and TLS requirements. Apply the reviewed migration only with separate staging authorisation.
3. Confirm the backup schedule and retention. Restore synthetic submissions and all related records into a disposable schema, compare references and row counts, and restart the staging application to verify persistence.
4. Authorise an SMTP sender and test inbox. Confirm the approved sender mailbox exists, TLS settings, credentials handling, outbound access and limits. Put the production owner recipient in server secrets only. Verify successful delivery and fault/recovery behavior using synthetic mail in staging.
5. Authorise an isolated Auth0 application and configure exact staging callback and logout origins, the owner subject, MFA enrollment and recovery. Verify expiry, non-owner rejection, session revocation and recovery.
6. After a manual dry run, authorise staging-only scheduling. Verify Node, environment injection, concurrent claims, timeouts and safe behavior when the process stops before or after acceptance. Test rate limits and header spoofing through the actual reverse proxy. Verify isolation from unauthenticated and unauthorised sessions, crawlers, search and cached responses.
7. Record evidence and obtain separate activation approval. The form, admin routes and mail remain disabled until those gates pass.

Local tests use synthetic input, mocked SQL connections, simulated verified sessions and a stub SMTP transport. Database compatibility, backup/restore, MFA, SMTP and cron still require staging evidence.
